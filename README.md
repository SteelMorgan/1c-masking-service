# 1c-masking-service

Внешний сервис маскирования ответов 1С-инструментов для ИИ-агента. Реализация —
`onec-masking-service` 0.1.0 (Rust/Axum): SQLite-хранилище, internal API на
Unix socket, human API/UI на отдельном TCP-listener.

Сервис получает результат вызова инструмента до его отдачи агенту: ФИО и
значения из словаря/правил заменяются обратимыми токенами вида
`[MASK:v1:<CAT>:<token>]`. Секреты вырезаются ещё в 1С на границе данных и
доезжают до сервиса как `[SECRET_REMOVED]` — это нормальное значение, не
сигнал. Раскрытие исходных значений возможно только человеку с ролью `Viewer`
через UI; агент и `Admin` раскрытия не получают. В историю и логи пишется
только замаскированная форма.

> **Рассчитан на определённый набор инструментов.** В текущем виде («как
> есть») сервис работает в связке
> [v8-session-manager](https://github.com/1c-neurofish/v8-session-manager)
> (MCP-хаб, вызывает сервис на каждый вызов инструмента) →
> [wt-mcp-adapter](https://github.com/SteelMorgan/wt-mcp-adapter) +
> web-transport-addin (транспорт 1С ↔ менеджер) →
> [1c-mcp-tools](https://github.com/SteelMorgan/1c-mcp-tools) (прикладной слой:
> инструменты данных и граница данных в 1С). Он опирается на их контракты:
> конверт ответа с `field_sources`, внутренние feed-инструменты, опознание базы
> по координатам ИБ. С другим MCP-сервером для 1С без доработки не заработает.
> Как устроена связка — транспортный и прикладной слои, жизненный цикл
> сессии: [схема стека](https://github.com/1c-neurofish/v8-session-manager/blob/main/docs/architecture/STACK_OVERVIEW.md).

## Быстрый старт

Нужны Rust stable + Cargo и Unix-подобная ОС (UDS, peer credentials, file
permissions). SQLite идёт через bundled `rusqlite`.

```sh
cargo build --release
```

Бинарник — `target/release/masking-service`. Миграции применяются при старте;
создаётся пользователь `Admin` без пароля — войти нельзя до bootstrap.

Локальный запуск без прав на `/var/lib` и `/run` — свои пути через ENV (полный
список — «Конфигурация (ENV)»), запуск сервиса и bootstrap первого Admin из
интерактивного TTY (клиент подключается к control socket работающего сервиса):

```sh
mkdir -p .local/run .local/data
export MASKING_DATABASE_PATH="$PWD/.local/data/service.sqlite3"
export MASKING_SOCKET_PATH="$PWD/.local/run/service.sock"
export MASKING_CONTROL_SOCKET_PATH="$PWD/.local/run/control.sock"
export MASKING_MANAGER_SOCKET_PATH="$PWD/.local/run/manager.sock"   # UDS менеджера
export MASKING_EXPECTED_ORIGIN="http://127.0.0.1:8787"

cargo run                           # сервис; human UI на MASKING_HUMAN_BIND (127.0.0.1:8787)

# во втором терминале, с теми же ENV, пока сервис запущен:
cargo run -- admin bootstrap        # пароль 12–1024 символа, спрашивается дважды
```

Bootstrap работает только через control socket; HTTP-маршрута у него нет,
после успеха он необратимо закрывается. Human listener рассчитан на localhost
или HTTPS reverse proxy: session cookie — `Secure`, поэтому прямой HTTP из
браузера с другого хоста не является рабочей схемой.

Дальше: войти в UI как `Admin`, создать `Viewer` (ссылка-приглашение),
подключить v8-session-manager (см. «Архитектура»), выбрать режимы
инструментов базы и настроить маскирование (см. «Настройка маскирования»).

**Docker.** В репозитории есть `Dockerfile` и пример `compose.dev.yml` для
тестового стенда: состояние — во внешнем volume, сокеты — в общем с
менеджером volume `/run/1c-masking`. Имена volume, порты, UID и путь в общем
volume задаются через ENV — образец в [.env.example](.env.example):

```sh
cp .env.example .env                 # подставьте свои значения
docker volume create masking-service-state   # имена — из MASKING_STATE_VOLUME / MASKING_SHARED_VOLUME
docker compose -f compose.dev.yml up -d --build
```

Умолчания имён внешних volume (используются, если в `.env` нет
`MASKING_STATE_VOLUME`/`MASKING_SHARED_VOLUME`):
`masking-service-state` — состояние сервиса (SQLite), `manager-shared-runtime` —
общий с менеджером каталог сокетов (`MASKING_SHARED_SUBPATH=run/1c-masking`).
Оба volume `external` и должны существовать до `up`; без `.env` с новыми
пустыми томами стенд поднимется с чистым состоянием (потребуется bootstrap
Admin через control socket). `down` данных не удаляет.

Каталог `deploy/dev-tunnel/` — пример SSH
reverse-туннеля к менеджеру для тестового стенда (см. его README).

**Опознание баз (RAS).** Для ряда операций (автоматическая привязка баз для
маскирования) менеджер работает с RAS-агентом кластера 1С: на его хосте
нужны исполняемый `rac` и сетевой доступ к RAS. Настройки задаются в env
процесса менеджера — `V8SM_RAC_PATH` (по умолчанию
`/opt/1cv8/current/rac`), `V8SM_RAS_ADDRESS` (опционально, по умолчанию
`<host из Srvr>:1545`), `V8SM_RAS_CLUSTER_USER`, `V8SM_RAS_CLUSTER_PASSWORD`
(логин/пароль опциональны, см. `.env.example` менеджера). Без доступного
RAS сервис работает с генерируемыми GUID, стабильно закреплёнными за парой
(Srvr, Ref) — ограничение режима: переименование или перенос базы требует
переназначения записи в админке.

## Архитектура

### Компоненты и зависимости

Сервис не самодостаточен: managed-поток проходит через
[v8-session-manager](https://github.com/1c-neurofish/v8-session-manager), а
граница данных и внутренние feed-инструменты живут в расширении 1С
[1c-mcp-tools](https://github.com/SteelMorgan/1c-mcp-tools).
Общая схема слоёв связки — [STACK_OVERVIEW](https://github.com/1c-neurofish/v8-session-manager/blob/main/docs/architecture/STACK_OVERVIEW.md).

#### v8-session-manager — шлюз (MCP-хаб)
- На **каждый** публичный вызов инструмента агентом (при `masking.enabled`)
  вызывает сервис: `preflight` → tool.call в 1С → `finalize` по UDS
  `masking.socket_path` (service.sock); идемпотентные терминальные события —
  `terminal`. Параметр `masking.managed_tools` устарел и игнорируется
  (непустое значение — предупреждение в логе): имя инструмента на маршрут не
  влияет, неизвестные инструменты отклоняет сервис.
- MCP-инструмент `masking_export_setup {database: <uuid>, include_tools?}` —
  read-only экспорт **действующей** версии настройки (`masking-setup/v1`) для
  агента; идёт мимо контура маскирования в `GET /internal/v1/setup/export`
  сервиса (ответ — только конфигурация: без значений словаря, токенов и
  истории). Ошибки возвращаются как `{exported:false, code, message}`:
  `MASKING_DISABLED`, `DATABASE_INVALID`, `NO_ACTIVE_VERSION`,
  `SERVICE_UNAVAILABLE`. Используется навыком первичной настройки.
- Совместимость: нужен v8-session-manager, в котором все вызовы инструментов
  идут через сервис маскирования и есть MCP-инструмент
  `masking_export_setup`. Более старый менеджер пропускает мимо сервиса инструменты вне
  `managed_tools` и не даёт агенту экспорт настройки.
- Поднимает UDS-listener `masking.internal_listen_path` (manager.sock) с
  единственным маршрутом `POST /internal/v1/tools/call`
  `{instance_id, name, arguments}` — через него сервис загружает
  метаданные и словарь. Доступ ограничен peer UID
  `masking.service_expected_uid`.
- Скрывает internal-инструменты от агента: имена из `masking.internal_tools`
  не попадают в `tools/list`, `tools/call` от агента отклоняется.
- Опознаёт базу автоматически: адаптер в `session.register` шлёт координаты
  ИБ (`cluster_server` = Srvr, `infobase_name` = Ref), менеджер один раз
  резолвит их через `rac` в пару GUID-ов и строит непрозрачный ключ
  `instance_id`: `ras:<cluster_guid>:<infobase_guid>` при успехе RAS либо
  `gen:<srvr>/<ref>` verbatim при его недоступности. Сервис ключует запись
  базы точным `instance_id` — координаты не участвуют в сравнении,
  нормализации и склейки записей нет по построению. Автоматического
  перехода `gen:` → `ras:` нет: при появлении RAS запись под новым ключом
  создаётся отдельно, настройки переносятся экспортом/импортом.
- Отдельно проверяет conversation-assertions агента (ключи `broker_*`) — на
  стороне сервиса криптографии агента нет.

#### 1c-mcp-tools — расширение 1С

- Инструменты данных (ядра перенесены из ROCTUP/1c-mcp-toolkit, см.
  «Благодарности») с границей данных `mcp_ROCTUPГраницаДанныхСервер`: секреты вырезаются **всегда**
  (без флагов), ответ — конверт
  `{schema_version:1, result:<бизнес-JSON>, field_sources:{schema, lineage}}`,
  сериализованный в `content[0].text`.
- Внутренние инструменты `mcp_internal_masking_metadata_feed` и
  `mcp_internal_masking_dictionary_feed`: аргументы `{selector, cursor}`,
  страница `{success, metadata | dictionary_values, next_cursor, final_chunk}`.

#### Транспорт 1С ↔ менеджер

wt-mcp-adapter + web-transport-addin используются как есть; сервис от них
напрямую не зависит.

### Поток данных

**Вызов агента:**

```
агент → manager /mcp
      → POST service.sock /internal/v1/calls/preflight   (разрешение MASK-токенов в аргументах)
      → 1С tool.call → граница вырезает секреты ([SECRET_REMOVED])
      → конверт {schema_version:1, result, field_sources{schema,lineage}}
      → POST service.sock /internal/v1/calls/finalize    (маскирование, запись masked history)
      → агент получает замаскированный result в content[0].text
```

Недоступность сервиса или отказ границы — fail-closed: агенту возвращается
нейтральная ошибка, сырые данные наружу не выходят.

**Загрузка метаданных/словаря (pull, инициирует сервис):**

```
pull worker (тик MASKING_PULL_INTERVAL_SECONDS) → durable-очередь v2_refresh_intents
→ POST manager.sock /internal/v1/tools/call {database_id, name, arguments:{selector,cursor}}
→ 1С internal feed → страницы до final_chunk
→ PolicySnapshot + строка cache_generations → атомарная замена RAM-снапшота → intent снят
```

Снапшот публикуется только после полного успешного прогона; при сбое остаётся
прежний активный. `cache_generations` — журнал прогонов (version, digest,
счётчики), `v2_refresh_intents` — durable-очередь «нужен refresh» (старое имя
таблицы сохранено). На старте сервис ставит intent на каждую enabled-базу,
Admin-мутации добавляют свои.

### Internal API (UDS `MASKING_SOCKET_PATH`)

Не публикуется TCP, не для браузера; каждый peer проверяется по UID
(`MASKING_MANAGER_UID`). Лимит JSON body — `MASKING_MAX_BODY_BYTES`
(8 МиБ по умолчанию).

- `POST /internal/v1/calls/preflight` — readiness базы/инструмента, резолв
  ранее выданных mask-токенов в аргументах;
- `POST /internal/v1/calls/finalize` — `outcome`:
  `{kind:"tool_result", result:<Value>}` (непрозрачный бизнес-JSON любой
  формы — объект, массив или скаляр; сервис маскирует его и сам оборачивает
  в публичную форму `{content:[{type:"text",text}], is_error}`; строка
  уходит в `text` дословно без повторной сериализации, а уже публичный
  `ToolCallResult` с `content[]` возвращается как есть без обёртки) или
  `{kind:"transport_error", error}` (нейтральный sanitized-ответ);
  опциональный `field_sources` для маскирования по source_path;
- `POST /internal/v1/calls/terminal` — идемпотентный ledger терминальных
  событий (`scope.kind`: `verified`/`unverified`);
- `GET /internal/v1/health/live`, `GET /internal/v1/health/ready?database_id=`;
- `GET /internal/v1/setup/export?database_id=<uuid>&include_tools=0|1` —
  экспорт действующей версии настройки для `masking_export_setup` менеджера.
  Выбора версии нет: агенту доступна только действующая. Нет действующей —
  `404 NO_ACTIVE_VERSION`, сбой хранилища — `SERVICE_NOT_READY`.

Неизвестная база создаётся в режиме `unconfigured` (`ACTION_REQUIRED`);
неизвестный инструмент — `deny-pending-review` (автодобавляется в список
инструментов базы с меткой «новый»). Стартовая классификация
(сидится при открытии БД): `data-mask` — `execute_query`,
`find_references_to_object`, `get_object_by_link`; `no-mask` —
`get_metadata`, `get_access_rights`, `get_link_of_object`.

Родительские каталоги сокетов и БД создаются процессом. Если
`MASKING_MANAGER_UID` не задан, gate доверяет UID самого сервиса — это не
замена отдельному service account.

## Human UI

Контракт HTTP API — [web/API.md](web/API.md). UI: `/`, `/viewer`, `/admin`,
`/activate/{token}`; статика `app.js`/`grid.js`/`app.css` отдаётся сервисом
без inline JS/CSS и внешних ресурсов (CSP `default-src 'self'`).
Аутентификация локальная: ровно две роли `Admin`/`Viewer`, Argon2id,
activation-токены (15 минут), отзываемые сессии (30 мин idle / 8 ч absolute),
CSRF + точный Origin, cookie `__Host-mask_session` (Secure, HttpOnly,
SameSite=Strict). Login/activation/bootstrap rate limit — 5/мин и 20/час на
ключ. CSRF токен привязан к сессии и выдаётся в ответах login/activate и
`GET /api/v1/session`; UI держит его только в памяти вкладки.

Стартовый экран `/` объединяет вход и активацию приглашения (код или ссылка
целиком). Если первый Admin ещё не задан (`GET /api/v1/status` →
`bootstrap_required`), вместо формы входа показывается инструкция CLI
bootstrap. `/activate/{token}` предпроверяет код и показывает логин до ввода
пароля; после установки пароля сессия выдаётся сразу (автовход).

- `Viewer`: базы → чаты → последние 30–50 masked reports; при открытии записи
  reveal конкретного history ID в своём database/chat scope вызывается
  автоматически — neutral report v1 (`text`/`table`), `Cache-Control:
  no-store`, не записывается обратно, не аудируется; раскрытые значения живут
  только в памяти вкладки, сбрасываются при уходе с записи, отличия от
  маскированного подсвечиваются. Если mapping недоступен (истёк TTL/рестарт),
  показывается маскированный отчёт с предупреждением. Переключатель
  «Оригинал» меняет вид без повторного запроса (маскированное/реальные).
  `Admin` reveal не получает. Табличные блоки отчёта рендерятся
  изолированным модулем `grid.js` (`window.MaskingGrid`): сортировка,
  фильтры по колонкам (для чисел — диапазон `a..b`), общий поиск, сброс
  фильтров/поиска/сортировки, «Копировать всё», скрытие колонок,
  постраничный вывод, закреплённая шапка, копирование ячейки кликом,
  размер шрифта A−/A+; колонки с маскированными значениями
  (`columns[].masked`) помечены замком и подсвечены. Экспорт CSV и
  «Копировать всё» выгружают то, что на экране: в маскированном виде —
  маскированные значения, в раскрытом — реальные. Первая выгрузка реальных
  значений в рамках раскрытия записи требует подтверждения в модальном окне
  (ответственность за их сохранность переходит к человеку, в чат с агентом их
  не вставлять); повторно для той же записи не спрашивается. Копирование
  одной ячейки кликом идёт без окна, но с уведомлением «Скопировано
  (реальное значение)». «Скопировать для агента» всегда маскированное.
  Заголовок отчёта — текст запроса/описание вызова (`report.title`, пишется
  на preflight в `call_contexts`) плюс статус и время записи; порядок
  колонок таблицы повторяет порядок запроса из `field_sources.schema.columns`.
  «Почему скрыто» (`GET /api/v1/history/{id}/reasons`): причины
  маскирования записи (правило, словарь с категорией, встроенное) с числом
  ячеек, подсветка ячеек выбранной причины, версия настройки, которой
  обработана запись, и ссылка для администратора на правило или источник.
  Для записей без сохранённой детализации — общие причины;
  истёкшая запись — `410`. Кнопка «Экспорт настройки…» в верхней панели
  выгружает действующую версию выбранной базы (флажок — с режимами
  инструментов); выбрать другую версию Viewer не может.
- `Admin`: пользователи (создание с серверной ссылкой приглашения, перевыпуск,
  сброс пароля новым приглашением, отключение, удаление никогда не входивших),
  отображаемое имя базы (`display_label`, переименование через PATCH), режим
  базы и оба TTL, строгий режим, refresh (с текстом последней ошибки и
  плашкой «нужна настройка»), классификация инструментов (легенда режимов,
  метка «новый», подтверждение bypass, удаление записи — для инструментов,
  снятых из 1С), «Настройка маскирования» — версии,
  черновик, импорт/экспорт, сравнение, сухой прогон, активация и откат (см.
  раздел ниже), «Журнал настройки». Словарь и правила редактируются только
  в черновике: источники выбираются в ленивом дереве метаданных
  `GET .../metadata` по RAM-manifest (до 100, только configuration с
  `filter_ast` — не raw values), условие источника задаётся конструктором
  (И/ИЛИ/НЕ, равно/не равно/одно из по полям `GET .../metadata?fields_of=`).

Mapping токенов живёт только в RAM: scope = database+chat, reverse key —
HMAC-SHA-256 с process-local ключом.
Рестарт теряет mapping → при старте `history` и `call_contexts` очищаются
полностью (нераскрываемая история — чистый риск хранения). Эффективный TTL
записи истории и контекста вызова — `min(history_ttl, mapping_ttl)` базы:
запись не переживает соответствия, без которых не раскрывается.
pull worker заново поднимает снапшоты enabled-баз через менеджер.

## Настройка маскирования: версии, импорт/экспорт, активация

Контракт маршрутов — [web/API.md](web/API.md), раздел «Версионированная
настройка (setup)».

**Версии.** Настройка базы (правила + словарь + режимы инструментов) —
версия в `policies`: `draft` (не больше одного черновика на базу), `active`
(не больше одной), `retired`. Действующая версия не изменяется: любое
изменение — черновик → сравнение → активация. Откат — «Вернуть эту версию»:
копия архивной версии становится новым черновиком (`setup/rollback`) и
активируется обычным путём, архив не меняется. Список версий с автором и
датой и содержимое любой версии — `setup/versions`, `setup/versions/{n}`
(только чтение, без журнала и аудита).

**Формат `masking-setup/v1`.** Контракт файла — §7 навыка
[masking-initial-setup](skills/masking-initial-setup/SKILL.md);
источник истины — парсер `src/domain/setup/parse.rs`.

**Действие `keep` — только структурное.** Правило `keep` по
`source_path`/`name`/`type` отменяет структурную маску поля (маску или
секрет всего значения по совпавшему селектору), но НЕ открывает значение
целиком: словарь и regex-правила продолжают маскировать совпадения внутри
поля, а встроенные маркеры (секреты, ФИО) действуют до проверки правил.
Поле, помеченное `keep`, «протекает» только
значениями, которых нет в словаре и не ловит ни один шаблон. В diff
добавление `keep` остаётся ослаблением (может подавить маску более
позднего селектора), снятие — усилением.

- **Экспорт** — `setup/export?version=active|draft|<n>&include_tools=0|1`
  (Admin: любая версия; Viewer: `/api/v1/databases/{id}/setup/export`,
  только действующая; агент: `masking_export_setup` через менеджер).
  Скачивание пишется в журнал настройки.
- **Импорт** — `POST setup/imports?replace_draft=0|1`: файл проверяется
  целиком (до 200 ошибок с местом в файле, например «Правило 3: …»), при
  успехе становится черновиком (`origin=import`). Если черновик уже есть —
  `409 DRAFT_EXISTS`, UI предлагает заменить. Импорт делает человек в UI.

**Сравнение (diff).** `setup/diff?from=active&to=draft|<n>` делит изменения
на **ослабления** (агент увидит больше: снято скрытие, добавлено «не
маскировать», сужен шаблон или условие источника, удалён источник,
инструмент переведён в bypass), **усиления** и нейтральные (обоснования,
приоритеты), плюс предупреждения (`PATH_NOT_IN_MANIFEST`, `SOURCE_LARGE`,
`DATABASE_MISMATCH`, `DICTIONARY_LIMIT`, `TOOL_NOT_SEEN`, …). Каждое
ослабление подтверждается отдельно, усиления принимаются построчно
(«Принимаю все» отмечает все), предупреждения по отдельным элементам можно
исключить из активируемой версии. Если у версии есть секция `tools`,
инструменты с записью классификации, которых в ней нет, приходят отдельным
нейтральным изменением `TOOL_REMOVED`: удаление записи принято по
умолчанию, снятый флажок оставляет инструменту текущий режим (вызов
удалённого инструмента потом отклоняется как непроверенный — это не
ослабление). Отсутствие секции `tools` (`null` или ключа нет) удалений
не создаёт.

**Активация.** `POST setup/activate` сервер перепроверяет в одной
транзакции: неподтверждённое ослабление — `409 WEAKENING_NOT_CONFIRMED`,
черновик изменился после сравнения — `409 DRAFT_CHANGED` /
`STALE_CONFIRMATION`, правила `secret` пока не применяются —
`409 SECRET_POLICY_UNSUPPORTED`. Непринятые усиления сервер откатывает к
состоянию действующей версии сам. После активации словарь перезагружается.
Правка черновика — `PUT setup/draft/{dictionary|rules|tools}` с
`If-Match: "<draft_hash>"` (параллельная правка — `409 DRAFT_CHANGED`).
Legacy-маршруты `PUT dictionaries`, `POST policies`,
`POST policies/{id}/activate` работают поверх версий: правят или создают
черновик, активируют только черновик и проходят ту же проверку ослаблений.

**Сухой прогон.** `POST setup/dry-run {version, limit≤50}` прогоняет
последние записи истории действующей версией и черновиком. Показывает,
какие ячейки станут скрыты или видны (маскированная сетка — только статусы
и координаты, без значений), время проверки (медиана, худшая запись,
превышения бюджета `MASKING_CHECK_BUDGET_MS`) и память словаря с крупнейшими
источниками. Новые источники словаря прогон не учитывает — их значения
загрузятся только после активации. История очищается при перезапуске
сервиса; пустая история — `history_empty`.

**Журнал настройки** — `setup/journal`: импорт (в т.ч. отклонённый, с sha256
файла), правки и удаление черновика, активация (подтверждённые ослабления,
непринятые усиления, исключения, комментарий), откат, экспорт, смена режима
инструмента, перенос при обновлении.

**Строгий режим** (`databases.strict_mode`, по умолчанию включён, тумблер в
«Основное»): см. раздел «Правила границы данных для запросов агента».

**Словарь: Aho-Corasick и прогрев.** Значения словаря ищутся в ответе одним
проходом автомата Aho-Corasick (`LeftmostLongest` для скрываемых значений,
отдельные автоматы для «не маскировать» и секретов) вместо перебора всех
значений. Автомат строится один раз при замене снимка базы (pull или
активация) в отдельном потоке, вне блокировки кэша; до завершения сборки
действует прежний снимок. После перезапуска сервис ставит обновление на
каждую включённую базу (`startup_rewarm`) и заново поднимает словари через
менеджер. Статистика источников (`cache_generations.source_stats_json`)
питает предупреждение `SOURCE_LARGE` и оценку памяти в сухом прогоне.
При pull с неизменным словарём пересборки автомата нет: отпечаток значений
(`dictionary_fingerprint`) совпал со снимком — автомат переиспользуется,
действия категорий пересчитываются дешёвым `with_actions`. Холодный старт
и первый прогрев (индекса ещё нет, data-mask не готов) агент видит как
понятный отказ: `503 SERVICE_WARMING_UP`, текст «Сервис маскирования
прогревает словарь, повторите через N с» и поле `retry_after_s` — оценку
по числу значений прошлого pull (≈10 с на 1 млн значений, минимум 5 с).
В MCP-ответе менеджера это `isError` с этим текстом, не transport_error;
`retry_after_s` дублируется в `structured_content.error`. Если прогрев не
идёт (нет ожидающего pull — `needs_attention` или intent снят), ответ
остаётся обычным `SERVICE_NOT_READY`. Отказ фиксируется терминально,
как все отказы preflight (менеджер пишет `calls/terminal`) — повтор идёт
с новым `call_id`.

**Повторы обновления (backoff).** При временной ошибке pull (например,
`MANAGER_UNAVAILABLE`) база переходит в `retrying`, следующая попытка —
через `min(base·2^(n-1), cap)` ± разброс (см. ENV). После
`MASKING_PULL_MAX_ATTEMPTS` неудач подряд — `needs_attention`: в списке баз
метка «Нужна настройка», в карточке базы — текст последней ошибки
(`refresh.last_error_text`), автоповторы прекращаются до ручного refresh.
Прежний снимок продолжает действовать.

`MANAGER_UNAVAILABLE` — менеджер не отвечает/недоступен. Отдельный случай
`DATABASE_NOT_CONNECTED`: менеджер жив, но маршрута к базе нет — живой
1С-сессии с координатами этой базы (`no_target`) нет, refresh остаётся в
`retrying`. Текст ошибки содержит координаты базы и подсказку проверить
сессию 1С.

## Безопасность: модель угроз и рекомендации по развёртыванию

**Для чего сервис.** Штатный режим работы ИИ-агента: не дать *случайно*, без
злого умысла, уйти ключам, персональным и другим чувствительным данным к
LLM-провайдеру и сервисам на пути к нему. Сервис маскирует то, что агент
получает в ответах инструментов. Целенаправленное извлечение данных агентом
(вопросы «да/нет» через условия запроса, посимвольный перебор и т. п.) в
модель угроз не входит: дешёвые меры против него есть (например, отказ, если
запрос упоминает секрет), но полной защиты сервис не обещает.

**Граница защиты — только инструменты.** Агент видит маскированные данные
только потому, что *всё* его взаимодействие с данными идёт через инструменты,
проходящие через сервис. Сами базы и хранилища держат данные открытыми.
Любой обходной путь сводит маскирование к нулю. Поэтому рекомендуется:

1. **Единый MCP-хаб.** Все инструменты агента, работающие с данными, —
   подключены через один шлюз (v8-session-manager) с маскированием. Это
   касается инструментов в обе стороны: и чтения, и записи. При записи
   маски в аргументах шлюз разворачивает в исходные значения только для
   инструментов в режиме «Маскировать данные» — в базу попадают настоящие
   значения, а ответ агенту снова маскируется.
2. **Маскирование по умолчанию для всех инструментов.** Новый или
   неизвестный инструмент запрещён, пока администратор не выберет ему режим
   в UI. Режим «Без маскирования» (класс `no-mask`): ответ
   передаётся агенту как есть — только для инструментов, которые не
   возвращают данных базы: метаданные, проверка синтаксиса, управление
   окнами и служебные операции.
   Первый вызов неизвестного инструмента автоматически добавляет его в список
   инструментов базы в режиме `deny-pending-review` с меткой «новый»
   (`auto_added`, время первого вызова, счётчик отклонённых вызовов).
   Перевод в «Без маскирования» (`no-mask`) требует явного подтверждения: `PUT tools/{tool}`
   без `confirm_bypass:true` отклоняется (`400 BYPASS_NOT_CONFIRMED`), а UI
   предупреждает, если имя похоже на чтение данных
   (`query|select|data|record|history|get_|read`). Импорт файла, переводящий
   инструмент в bypass, считается ослаблением и подтверждается отдельно.
3. **Никакого прямого доступа агента к базам любого вида:** СУБД 1С,
   файловые базы, `.dt`/`.cf` выгрузки с данными, базы журналов и
   логов (например, ClickHouse с журналом регистрации), SQLite самого
   сервиса, резервные копии, общие каталоги с выгрузками. У окружения
   агента не должно быть учётных данных к ним и сетевого маршрута до них.
4. **Другие MCP-серверы** (логи, мониторинг, файлы) либо не подключаются к
   агенту, работающему с боевыми данными, либо подключаются через тот же
   шлюз с маскированием.
5. **Учётная запись 1С агента** — только чтение там, где запись не нужна.

Окружение разработки (DEV-база, отладка самого сервиса) может нарушать
пункты 3–4 осознанно; на боевых данных — нет.

### Правила границы данных для запросов агента

Граница данных в 1С (`mcp_ROCTUPГраницаДанныхСервер`) и сервис решают, что
можно отдать, по происхождению каждой колонки результата. Действующие правила:

| Правило | Зачем |
|---|---|
| Колонка без доказанного исходного реквизита — отказ `SOURCE_LINEAGE_UNVERIFIED`, кроме допущенных безисточниковых видов (следующая строка) | под нейтральным псевдонимом может оказаться секрет (`Пользователь.apiKey КАК Комментарий`) |
| Без исходного реквизита допустимы только колонки, которые агент написал сам: литералы, `ЗНАЧЕНИЕ(...)`, простые параметры, `КОЛИЧЕСТВО(...)` и выражения только из них. Граница помечает такую колонку `sourceless` ∈ `count`/`literal`/`parameter`/`value`/`composite`; сервис допускает только эти виды и только примитивные значения ячеек (`count` — строго числа; ссылка от `ЗНАЧЕНИЕ` сериализуется плоским объектом `_objectRef` в `value`/`composite`, её строковые поля маскируются сервисом как обычные) | это не данные базы |
| Параметр безопасен, только если его фактическое значение примитивное (строка, число, дата, булево) и он не разыменовывается и не передаётся в `ПРЕДСТАВЛЕНИЕ`/`ВЫРАЗИТЬ` к ссылке. Ссылка и массив/список значений со ссылками — отказ | параметры приходят из JSON и умеют восстанавливать ссылки: `ВЫБРАТЬ &Контрагент.ИНН` прочитал бы базу |
| Таблица значений в параметре (`ИЗ &ТЗ`, `ПОМЕСТИТЬ ... ИЗ &ТЗ`) — жёсткий отказ всего запроса, без разбора колонок | через ссылку в таблице можно разыменовать реквизиты; состав ТЗ сервису не доказуем |
| **Чужой менеджер временных таблиц запрещён**: запрос выполняется без внешнего `МенеджерВременныхТаблиц`; источник — временная таблица, созданная не в этом же пакете, — отказ | происхождение данных такой таблицы неизвестно; правило защищает от будущей доработки «для удобства» |
| Фактические типы колонок берутся из результата (`РезультатЗапроса.Колонки[i].ТипЗначения`), без повторного выполнения запроса. Тип только ужесточает проверку, но не доказывает безопасность | `ВЫРАЗИТЬ(ИНН КАК Число)` даёт тип `Число`, а внутри ИНН |
| Имя секретного реквизита (режим пароля или имя вида `apiKey`, `secret`, `passphrase`) в любом сегменте пути вне списка выборки — `ГДЕ`, соединения, сортировка, группировка, итоги, выражения-вычисления, включая вложенные подзапросы, `ВЫРАЗИТЬ` и временные таблицы пакета — отказ. Секретный реквизит, выведенный колонкой как есть с доказанным lineage, — не отказ: вырезается `[SECRET_REMOVED]` | сравнение с секретом позволяет узнать его по частям |
| **Строгий режим** (настройка базы, включён по умолчанию, тумблер в админке базы): вместо отказа непроверенная колонка отдаётся, но маскируется целиком — все значения, включая булево и `NULL`, типизированным токеном `UNVERIFIED_*`; при выключении `unverified`-маркер от границы — отказ | даёт отлаживать сложные запросы без раскрытия данных; булево/`NULL` открытыми были бы каналом утечки |
| Маски в аргументах разворачиваются в исходные значения только для инструментов в режиме «Маскировать данные»; для остальных маска в аргументах — отказ `MASK_TOKEN_INVALID` | инструмент без маскирования, возвращающий аргументы эхом, раскрыл бы значение |
| Все вызовы всех инструментов идут через сервис; неизвестный инструмент запрещён до выбора режима администратором | см. пункт 2 выше |
| Ошибка **разбора** запроса (до исполнения: `СхемаЗапроса` + `НайтиПараметры`) возвращается агенту как `{success:false, error:"QUERY_PARSE_ERROR", message, position}` — текст платформы без префикса модуля, не длиннее 2000 символов, секретные маркеры вырезаны, `message` дополнительно проходит маскирование сервиса. Ошибка **исполнения** — только код `QUERY_EXECUTION_ERROR`, без текста. Если в аргументах вызова были mask-токены, которые сервис развернул в исходные значения, `message` снимается целиком, остаются код и позиция (`строка, колонка`) | агенту нужен текст синтаксической ошибки, чтобы исправить запрос; текст ошибки исполнения и эхо запроса после подстановки значений могут содержать данные |

Список секретных реквизитов захардкожен в границе 1С:
`mcp_ROCTUPГраницаДанныхСервер.ЭтоИмяСекрета` (Module.bsl, маркеры
имён вида `password|token|apikey|пароль|токен|секрет|ключ`…),
`СодержитСекретВТексте` (маркеры `key=value`/PEM в тексте) и флаг
режима пароля реквизита метаданных. Добавить секрет — правка кода
расширения 1c-mcp-tools. Настраиваемого списка в 1С (например, регистра
сведений) нет намеренно: такой список обязан быть доказуемо
недоступным для записи инструментам агента, а такая защита пока не
реализована — иначе агент мог бы снять секретность с реквизита и прочитать его.
Действие `secret` в правилах сервиса недоступно намеренно
(`SECRET_POLICY_UNSUPPORTED` при активации).

Чего сервис **не** предотвращает (осознанно, см. модель угроз): выводы о
значениях ИНН, ФИО и т. п. через условия запроса (`ГДЕ ИНН = "[MASK:…]" И
ПОДСТРОКА(ИНН, 1, 1) = "7"`), число строк, совпадение масок одинаковых
значений внутри чата.

### Лимиты обработки

- Превышение любого лимита — fail-closed (ошибка, а не частичный результат).
- Mapping: до 100 000 записей всего, 20 000 на базу, 10 000 на чат; до
  10 000 кандидатов маскирования на вызов. Maintenance-тик каждые 300 с:
  до 2 000 mapping, 500 history, 500 unscoped terminal, 500 audit записей.
  TTL mapping и history задаются на базу (по умолчанию 86 400 с).
- Pull: до 10 000 страниц на поток, до 1 000 000 значений словаря / 1 ГиБ,
  до 100 source paths и 100 selectors, cursor ≤ 1 МиБ, значение ≤ 2 МиБ.
- Настройка: файл ≤ 1 МиБ, до 200 ошибок разбора в ответе,
  сухой прогон — до 50 записей и 2 000 изменившихся ячеек на запись.
- Движок не делает NER/морфологию: FIO — по именам полей, source-literals из
  `field_sources` и ограниченному regex (`Фамилия Имя [Отчество]`), словарь —
  по точным строкам (подстроки, с учётом регистра; поиск — автомат
  Aho-Corasick). Склонения, опечатки и перестановки не гарантируются —
  администратор задаёт явные правила под фактические данные.
- Значение `[SECRET_REMOVED]`, пришедшее от 1С, сохраняется как есть;
  `cut_secrets` в сервисе — defence-in-depth поверх 1С-границы (имена полей,
  secret-паттерны, `Secret`-правила, `password_mode` source paths).

### Тесты

`cargo test --all-targets` — интеграционные файлы `tests/` (core service,
internal API, mapping, human auth, setup API/export/versions, индекс
словаря, backoff обновления) плюс
unit-тесты. `cargo fmt --check` и
`cargo build --release` — обязательные gate-ы.

Вручную проверены сквозные сценарии с менеджером и 1С на тестовом стенде:
pull словаря через `manager.sock`, маскирование ФИО, fail-closed при
остановке сервиса, Viewer reveal, фильтры словаря `part`/`filter_ast`; в
браузере — импорт → сравнение → сухой прогон → активация усиления →
«Почему скрыто» на свежем вызове → откат к исходной настройке.

### Статус и что не поставляется

Статус — development snapshot (0.1.0). Не поставляется: TLS в бинарнике, reverse proxy, systemd unit, OS service
account, backup/rotation, SQLite-шифрование, мониторинг. Сервис доверяет
границе менеджера и `database_id` из его конфигурации; peer-UID gate не
заменяет бизнес-авторизацию 1С. Production deployment не заявляется.
