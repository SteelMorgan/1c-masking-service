# Первичная настройка маскирования

Навык формирует стартовый файл настройки `masking-setup/v1` для базы 1С:
контекст базы → классификация реквизитов → правила и словарь → файл +
отчёт человеку. Агент **не импортирует** файл сам: импорт, проверку diff
и активацию выполняет человек-администратор в UI сервиса маскирования.

## Цель

Маскирование защищает персональные данные, секреты доступа, коммерческую
и иную чувствительную информацию от LLM-провайдера и сервисов на пути
ответа. Агент при этом должен оставаться полезным: анализировать как
аналитик, отлаживать, изучать проблемы и данные — не получая реальных
значений. Цель — **не «скрыть максимум»**, а скрыть минимум, достаточный
чтобы агент не узнал реальных субъектов и их чувствительные сведения;
остальное открыто. Лишняя маска — тоже дефект.

## Главный принцип: маскируем идентичность, а не факты

Факты (статусы, даты, количества, суммы, типы, коды справочников, связи)
нужны агенту для работы. Токен маски детерминирован: одно значение =
один токен — агент группирует, сравнивает и связывает записи без
значений. Корректный вывод агента: «у клиента [MASK:…] 3 просроченных
заказа на 1,2 млн» — связь и сумма есть, субъекта нет.

**Четыре вопроса к каждому полю:**

1. Указывает на конкретного человека/организацию/счёт вне системы (само
   или в сочетании)? → `mask`.
2. Даёт доступ или право действовать (ключи, пароли, токены)? → это
   секрет доступа: режется на границе 1С правкой кода расширения
   (`mcp_ROCTUPГраницаДанныхСервер.ЭтоИмяСекрета`), **не** файлом —
   см. «Секреты» ниже.
3. Раскрытие вредит коммерчески? → обычно маскируем связь (контрагента),
   а не число; число — только если чувствительно само по себе (анкета
   §0 п.3).
4. Нужно для анализа/отладки и на 1–3 ответ «нет»? → открыто.

Сомнительное — не решать молча: в отчёт человеку с аргументами «за и
против» (§«Серые зоны»).

**Таблица инструментов** (чем резать):

| Ситуация | Инструмент |
|---|---|
| Всё поле чувствительно | `source_path`/`name` mask |
| Значения утекают в другие поля (комментарии, представления, тексты ошибок/логов) | словарь |
| Распознаётся по форме (телефон, email, карта) | `regex` |
| Свободный текст целиком | не маскировать (убивает отладку) — словарь + regex по вхождениям |

**Критерии словарного источника** — все три: значение идентифицирует
субъекта; встречается вне своего поля; список конечный и управляемый.
Не брать в словарь: справочные нечувствительные (валюты, статусы,
номенклатура, если она не тайна); **ID событий** — высококардинальные
технические (GUID, номера документов/ордеров, суммы): исчерпание
автомата и отсутствие пользы; короткие значения <4 символов и
общеупотребительные слова; собственную организацию (если это не
явное требование). **ID субъектов** (uid, метки и логины аккаунтов)
с конечным управляемым списком — в словарь можно: формально они
«технические ID», но удовлетворяют всем трём критериям — агент
связывает по ним субъекта в любом тексте.

## Когда применять

| Триггер | Действие |
|---------|----------|
| «Настрой маскирование для базы X», «сгенерируй файл правил» | Весь поток §0–§5 |
| В базе уже есть активная настройка | Мерж поверх экспорта (§1), только усиления |
| Человек просит проверить/исправить готовый файл | §6 + чек-лист самоконтроля |

**Не применять** для: сухого прогона маскировщика (есть UI «Проверка»),
диагностики конкретного запроса, импорта/активации — их делает человек.

## Предусловия

- Есть MCP-доступ к 1С через маскирующий шлюз: инструменты `get_metadata`,
  `execute_query`, `masking_export_setup`.
- Известен `database` — UUID базы в реестре сервиса маскирования
  (берётся из `masking_export_setup` или выдаётся оператором).
- Значения реквизитов, возвращаемые `get_metadata`/`execute_query`,
  могут приходить уже замаскированными — для настройки нужны только
  **имена и пути** метаданных, значения не используются.

## 0. Контекст базы (анкета — до классификации)

По метаданным определить предметную область: имя конфигурации,
состав подсистем, ключевые объекты (`get_metadata()` сводка).
Затем задать человеку анкету — ответы идут в отчёт и в
`generated_by.note` файла:

1. Чьи персональные данные в базе (клиенты-физлица, сотрудники,
   пациенты, учащиеся)?
2. Есть ли особые категории (здоровье, биометрия, судимость,
   убеждения)?
3. Какие числа чувствительны сами по себе (зарплаты, индивидуальные
   цены, маржа, остатки на счетах)?
4. Какие организации публичны, какие — скрывать?
5. Какие внешние ID нужны агенту для отладки открытыми (номера заказов,
   ID транзакций, трек-номера)?
6. Нормативный режим (ПДн, банковская/врачебная/налоговая/коммерческая
   тайна)?

Если человек не отвечает — применять консервативные умолчания (см.
ниже) и прямо сказать об этом в отчёте.

## Каталог классов (универсальный)

| Класс | Примеры | Действие |
|---|---|---|
| Идентичность физлица | ФИО, логин, фото, подпись | `mask` + словарь |
| Контакты | телефон, email, адрес, мессенджеры | `mask` + regex в тексте |
| Гос-идентификаторы | паспорт, ИНН физлица, СНИЛС, полис | `mask` |
| Особые категории | здоровье, диагнозы (включая коды/справочники диагнозов в записи субъекта), биометрия | `mask` |
| Финансовые реквизиты | счёт, карта, IBAN, БИК+счёт | `mask` + regex |
| Идентичность юрлица-клиента | наименование, ИНН юрлица | по анкете п.4 |
| Внешние ID аккаунтов/субъектов | CRM-id, лицевой счёт клиента, номер карты лояльности, uid/метки аккаунта | `mask` (+ словарь при конечном списке) |
| Внешние ID событий | заказ, транзакция, трек-номер | по анкете п.5, умолчание `mask`; в словарь не брать |
| Числа, чувствительные сами по себе | зарплата, индивидуальная цена, остаток на счёте | по анкете п.3 |
| Секреты доступа | ключи, пароли, токены | граница 1С (правка кода расширения), не файл |
| Факты | статусы, даты, количества, типы, связи | открыто |

Категории в файле — соглашение навыка (`SECRET`/`FIO`/`PII`/`EXTID`/
`AMOUNT` и т.п.; сервис хранит категорию строкой ≤64 символов для
правил, ≤32 для словаря). При наличии действующей настройки
**переиспользовать категории из экспорта**.

**Секреты.** Действие `secret` в файле запрещено guard'ом активации
(`409 SECRET_POLICY_UNSUPPORTED`) — не писать никогда. Встроенные
маркеры границы 1С и так режут имя поля до маскировщика — проверка
по нормализованному имени (нижний регистр, удалены `_` и `-`).
Единственный источник списка маркеров на границе — функция
`mcp_ROCTUPГраницаДанныхСервер.ЭтоИмяСекрета` расширения 1С
(текстовые маркеры в значениях — `СодержитСекретВТексте` там же;
список не копируется сюда, чтобы не разойтись с кодом).
`mask`-правило по имени добавляет покрытие для
нестандартных имён и делает намерение явным. Секрет вне встроенных
маркеров — в отчёт человеку как кандидат на правку кода расширения.
Настраиваемый список в 1С отложен:
он обязан быть недоступным для записи инструментам агента — такая
защита не решена.

**Консервативные умолчания без анкеты.** Скрыты: идентичность,
контакты, особые категории, финансовые реквизиты, все внешние ID, все
юрлица. Суммы открыты, кроме явно зарплатных/тарифных. В отчёте явно
сказать, что применены умолчания, и перечислить, что можно открыть
после ответов.

**Квазиидентификаторы.** Поля, безопасные по одному, в сочетании
указывают на человека (дата рождения + город + пол; редкий диагноз +
дата приёма). Такие комбинации в одном объекте отмечать и маскировать
хотя бы одно звено (обычно дату рождения/точный адрес).

## Поток

### 1. Текущее состояние

Вызвать `masking_export_setup(database=<uuid>)`. Ответ:

- `404 NO_ACTIVE_VERSION` — настройки нет, строим файл с нуля
  (`database_hint.source_version` не заполнять);
- успех — активная версия: файл строим **поверх неё** (добавляемые
  элементы мержим в существующие `rules`/`dictionary.sources`,
  дедупликация по идентичности — см. ниже).

**По умолчанию файл только усиливает**: новые `mask`-правила и новые
источники словаря добавляем; существующие правила и источники из
экспорта переносим как есть (никогда не удаляем `mask`, не добавляем
`keep`, не сужаем шаблоны, не снимаем источники). Ослабление — только
по явному запросу человека и с отдельной пометкой в отчёте.

Переносимое — байт-в-байт из экспорта: **не переписывать** `reason`,
`filter`, `estimated_values` перенесённых элементов без функциональной
нужды — каждое косметическое изменение даст нейтральный шум
`REASON_CHANGED`/`FILTER_CHANGED` в diff и замаскирует реальные
изменения. `estimated_values` заполняем только новым источникам.
Экспорт подставляет отсутствующему `reason` плейсхолдер
«не указано (создано до версионирования настройки)» — это маркер
старых записей, переносим как есть, не «исправляем».

`include_tools=1` — снимок режимов инструментов; секцию `tools` в файл
добавляем только если человек попросил изменить режимы. Режимы —
`tools[].mode ∈ data-mask` (ответ маскируется) `| no-mask` (ответ
уходит агенту как есть — только для инструментов без данных базы;
при переводе сервер потребует `confirm_bypass` — решение человека)
`| deny-pending-review` (вызов отклоняется; дефолт для новых
инструментов).

### 2. Метаданные

Через `get_metadata`:

- `get_metadata()` — сводка корневых типов с количествами;
- `get_metadata(meta_type=..., name_mask=..., offset/limit)` — списки
  объектов (`Справочник`, `Документ`, `РегистрСведений`, `РегистрНакопления`,
  `ПланВидовХарактеристик` и т.п.);
- `get_metadata(filter="<Тип>.<Имя>")` — структура объекта (Реквизиты,
  Измерения, Ресурсы, ТабличныеЧасти, СтандартныеРеквизиты);
- `get_metadata(attribute_mask="<подстрока>")` — поиск реквизитов по
  имени/синониму сразу по конфигурации — быстрый способ найти
  кандидатов (`attribute_mask` по каждому маркеру каталога классов).

Объекты данных для обхода: справочники, документы, регистры сведений/
накопления, планы видов характеристик, бизнес-процессы/задачи —
всё, чьи поля могут попасть в ответы инструментов. Перечисления и
константы обычно пропускаем.

Особенности выдачи `get_metadata`:

- `attribute_mask` возвращает и обработки/отчёты — их реквизиты не
  данные базы; выдачу фильтровать по классу объекта, брать только
  объекты данных из списка выше;
- `attribute_mask` не возвращает тип поля: перед добавлением поля в
  источники словаря тип проверять отдельным
  `get_metadata(filter="<Тип>.<Объект>")` — нужна строка;
- при больших списках пагинировать `offset/limit`; эпизодический
  ответ «Операция временно недоступна» — повторить запрос (проходит
  с ретраем, причина на стороне шлюза).

Критерий полноты обхода (он же обоснование числа «обойдено N
объектов» в отчёте): `attribute_mask` прогнан по **всем** маркерам
таблицы §3 плюс маркерам профиля области; структура (`filter=`)
просмотрена у каждого объекта со срабатываниями и у каждого
справочника субъектов из профиля — даже без срабатываний по имени
(ФИО может лежать в стандартном `Наименование`, а чувствительность —
в синониме, которого нет в имени).

Формат `source_path` правил и источников — **плоский** путь
`<Класс>.<Объект>.[ИмяТЧ.]Поле` (форма манифеста сервиса, без сегментов
`Реквизит`/`Измерение`/`Ресурс`/`ТабличнаяЧасть`):

```
Справочник.Контрагенты.НаименованиеПолное
Справочник.ФизическиеЛица.ФИО
Документ.ЗаказКлиента.Товары.Комментарий
РегистрСведений.ДанныеКарт.НомерКарты
```

`get_metadata` отдаёт полный `ПолноеИмя()` вида
`Документ.X.ТабличнаяЧасть.Y.Реквизит.Z` и
`РегистрСведений.X.Измерение.Z` — для `source_path` в файле сегменты
`ТабличнаяЧасть`, `Реквизит`, `Измерение`, `Ресурс`, `СтандартныйРеквизит`
удаляются, остаётся `X.[Y.]Z`. Файл с полной формой импорт примет, но
diff покажет `PATH_NOT_IN_MANIFEST` по каждому такому пути.

(Формы `Catalog.X`, `Document.X` тоже допускаются; регистр имени — без
учёта по Unicode.)

### 3. Классификация реквизитов

Классификация — по каталогу классов выше, с приоритетом **секреты >
идентичность/контакты/особые категории > внешние ID > чувствительные
числа**. Маркеры для `attribute_mask`/`name`-правил (без учёта
регистра, сузить короткие чтобы не ловить лишнее):

| Класс | Маркеры RU/EN в имени/синониме | Категория | Действие |
|---|---|---|---|
| Секрет | `password`, `passwd`, `passphrase`, `секретнаяфраза`, `secret`, `apikey`, `api_key`, `token`, `privatekey`, `accesskey`, `refreshkey`, `authorization`, `авторизац`, `парол`, `токен`, `секрет`, `секретныйключ`, `ключapi`, `ключапи` | `SECRET` | `mask` |
| ПДн-ФИО | `фио`, `fio`, `фамилия`, `surname`, `fullname`, `наименованиеполное` (у справочников людей/контрагентов) | `FIO` | `mask` |
| ПДн-контакты | `телефон`, `phone`, `email`, `почта`, `адрес`, `address`, `skype`, `telegram` | `PII` | `mask` |
| ПДн-документы | `паспорт`, `passport`, `инн`, `снилс`, `документудостовер`, `датарождения`, `birthday` | `PII` | `mask` |
| Особые категории | `диагноз`, `здоровье`, `биометр`, `судимост`, `убежден`, `диагноз`+коды | `PII` | `mask` |
| Финансовые реквизиты | `счет`, `iban`, `карта`, `card`, `бик`, `bic`, `корсчет` | `PII` | `mask` |
| Внешние ID аккаунтов/субъектов | `account`, `clientid`, `uid`, `subaccount`, `кошел`, `wallet` | `EXTID` | `mask` |
| Внешние ID событий | `ordid`, `clordid`, `tradeid`, `заказ`, `order`, `track`, `трек` | `EXTID` | по анкете п.5, умолчание `mask` |
| Чувствительные числа | `зарплат`, `salary`, `оклад`, `тариф`, `маржа` | `AMOUNT` | по анкете п.3 |
| Суммы прочие (опционально) | `сумма`, `amount`, `balance`, `баланс`, `price`, `цена`, `объём`, `qty` | `AMOUNT` | `mask` или пропуск — по запросу человека |

`Наименование` — стандартный реквизит каждого справочника; у
справочников людей и контрагентов (ФизическиеЛица, Пользователи,
КонтактныеЛица и т.п.) в нём лежит ФИО/название. Name-правило
`*Наименование*` не заводить никогда — замаскирует все справочники,
включая валюты и инструменты; только `source_path` вида
`Справочник.X.Наименование` по конкретным справочникам + источник
словаря по тому же полю (закрывает ссылки — см. §5).

Типовые ложные срабатывания маркеров — перед заведением name-правила
смотреть всю выдачу `attribute_mask` по нему:

| Маркер | Что ловит лишнего |
|---|---|
| `инн` | `ИспользоватьКлючПроверкиПодлинности…` («подлИННости») |
| `uid` | `РегламентноеЗаданиеGUID`, `ВерсияGUID` («gUID») |
| `адрес` | `ОбъектАдресации` (роли бизнес-процессов) |
| `счет` | `ВидРасчета`, `ДатаРасчета`, `СчетФактура` |
| `email` | флаги и настройки транспорта `EMAIL*` |
| `бот` | `Обработка…`, `Обработчик…` |

Правило: короткий маркер с ложными попаданиями — не name-правило,
а `source_path` по списку реально найденных полей.

Известное ограничение: маркер `ключ` в файле не использовать —
`*ключ*` ловит `КлючСвязи`/`КлючСтроки`/`КлючАналитики` повсюду;
только суженные формы (`ключapi`, `секретныйключ` и т.п.).

Псевдонимы: поле с нейтральным именем, чей источник чувствителен,
резать по `source_path`, а не по имени — `get_metadata` показывает
реальный реквизит, а не алиас запроса.

### 4. Правила

Два стиля, оба валидны по F4 (шаблоны `*` — всё; `*x*` — «содержит x»;
иначе — точное совпадение; `*.Код`/`Справочник.*` — НЕ шаблоны, а
точные строки — так писать нельзя):

- **`name`** — `*<маркер>*` по имени поля/колонки результата. Ловит
  поле под любым источником и псевдонимом. Для коротких маркеров
  проверять ложные срабатывания (`*код*` ловит и `КодТовара` — если это
  нежелательно, сужать маркер или переходить на `source_path`).
- **`source_path`** — точный путь реквизита из `get_metadata`.
  Точечно и предсказуемо; не ловит вычисляемые колонки без источника.

Рекомендуемая раскладка: `name`-правила по маркерам §3 + `source_path`
для точных попаданий, которые маркеры не ловят (например, поле
`Представление` с ФИО) или ловят лишнее.

- `action`: `mask` (единственное генерируемое; `keep` не добавляем,
  `secret` — см. «Секреты» выше).
- `category` — из §3.
- `priority` — 0 по умолчанию; повышать только для разрешения
  конфликтов (действие решает строгость, priority — тай-брейк между
  равными).
- `reason` — обязательно, 1..500 символов: почему элемент внесён
  (класс + маркер), например `ПДн: имя реквизита содержит "паспорт"`.
- `regex`-правила — только по явной необходимости; для mask-регекса
  обязателен `tests.match` (≥1 примера), рекомендуется `tests.no_match`.
- `type`-селектор — для полей по типу (`Строка(200)` и т.п. из
  `get_metadata` секций properties) — редко, только когда класс
  определяется типом, а не именем.
- `dictionary`-правила (`selector:"dictionary"`) задают действие для
  **категории** словаря: добавлять `mask` для каждой категории,
  введённой в §5.

### 5. Словарь (`dictionary.sources`)

Словарь — известные значения из базы, которые маскируются при любом
их появлении в ответе (точное совпадение подстроки, регистр учитывается),
в том числе внутри полей под `keep` — `keep` снимает только структурные
маски (name/type/source_path), словарь продолжает действовать. Брать
только источники по критериям из «Главного принципа».

**Ссылки и представления.** Ссылочное поле (`Документ.X.Контрагент`,
`РегистрСведений.Y.Аккаунт`) приходит в ответе как представление
ссылки — строка `Наименование` связанного объекта. `source_path`-
правило на `Справочник.X.Наименование` закрывает **только само поле**
справочника; ссылки на него из документов, регистров и ТЧ таким
правилом не маскируются. Их закрывает только словарь по тому же
`Наименование` (представление ссылки совпадает со значением
источника). Практика для каждого справочника субъектов/аккаунтов:
`source_path` на `Наименование` + источник словаря по нему же —
тогда маскируются и поле, и все ссылки на объект.

- `mode`: `part` + список `sources` (формат `all` — только если все
  строковые поля заведомо словарные; в первичной настройке не
  использовать без запроса).
- `source_path` — путь **строкового** реквизита/измерения/ресурса
  (тип проверять в `get_metadata`: секции `Реквизиты[].Тип` и т.п.).
  Нестроковые поля сервис отклонит при pull
  (`DICTIONARY_SOURCE_TYPE_UNSUPPORTED`); passwordMode-поля и
  секретные по имени — тоже (`DICTIONARY_SECRET_SOURCE_DENIED`).
- `category` — категория значений (≤32 символов; та же, что в
  `dictionary`-правиле §4).
- `filter` — опциональный AST отбора строк источника:
  `{"op":"eq","field":"<Поле>","value":<знач>}`,
  `{"op":"in","field":"<Поле>","values":[...]}`,
  `{"op":"and","args":[...]}`, `{"op":"or","args":[...]}`,
  `{"op":"not","arg":{...}}`. Поля — реквизиты того же объекта,
  что и `source_path`. Типовое применение — вырезать
  служебные/технические записи (служебные учётные записи,
  предопределённые элементы) и уменьшить объём. Отбор по
  `ПометкаУдаления` уместен, только когда помеченные записи
  заведомо не несут чувствительных значений либо не доходят до
  ответов инструментов — иначе фильтр ослабляет защиту.
- `estimated_values` — оценка количества значений (см. ниже);
  заполнять только новым источникам, у перенесённых не трогать.

**Оценка объёма.** Для каждого источника через `execute_query`:
`ВЫБРАТЬ КОЛИЧЕСТВО(*) ИЗ <Тип>.<Объект>` — с `ГДЕ`, повторяющим
`filter` источника, если тот задан (иначе оценка завышена).
`КОЛИЧЕСТВО(РАЗЛИЧНЫЕ <Поле>)` точнее, но граница отклоняет агрегат
над уже маскируемым полем — для полей под действующими правилами
`КОЛИЧЕСТВО(*)` единственный рабочий путь (верхняя оценка с дублями).
Результат записать в `estimated_values`. Если значений больше порога
предупреждения о крупном источнике (на сервисе — env
`MASKING_SOURCE_LARGE_VALUES`, дефолт `100_000`; жёсткий лимит pull —
1 000 000 значений / 1 ГиБ суммарно), то:

- уменьшить источник `filter`'ом; или
- оставить и **явно предупредить в отчёте**: импорт покажет
  `SOURCE_LARGE` (оценка времени загрузки и памяти автомата);
- источники сверх жёсткого лимита не добавлять — pull упадёт с
  `FEED_LIMIT_EXCEEDED`.

### 6. Файл и отчёт

Файл — UTF-8 JSON по схеме §7, ≤1 МиБ, без внутренних ID
(`policy_id`/`rule_id`/`config_id`), без значений данных (значения
допустимы только внутри `filter` отборов и `tests` примеров —
никаких реальных секретов и ПДн).

`database_hint`: `id` = UUID целевой базы, `label` — её имя,
`source_version` — версия активной настройки из экспорта §1
(для мержа поверх).

Отчёт человеку (обязательный результат навыка):

- ответы на анкету §0 — или явная строка «ответов нет, применены
  консервативные умолчания» + список того, что можно открыть после
  ответов;
- сколько объектов метаданных обойдено, сколько полей классифицировано
  по классам (таблица класс → поля → правило name/source_path);
- что сознательно оставлено открытым и почему — по классам
  (факты, публичные организации, технические ID из п.5 анкеты);
- найденные квазиидентификаторы и какое звено замаскировано;
- серые зоны: по каждой — выбранное умолчание, почему, альтернатива;
- список источников словаря с `estimated_values` и предупреждениями
  о крупных;
- что взято из текущей настройки (мерж) и что добавлено — только
  усиления;
- маркеры с ложными срабатываниями, поля, которые не удалось отнести
  (списком для ручного решения);
- кандидаты в секреты для правки кода границы (если найдены) —
  функция `ЭтоИмяСекрета`, см. «Секреты»;
- куда сохранён файл; напоминание: импорт и активацию делает
  человек в UI (импорт создаёт черновик, diff покажет изменения);
  после импорта человеку стоит запустить **сухой прогон** в UI
  и оценить охват.

## 7. Формат `masking-setup/v1`

Обязательные поля верхнего уровня: `schema`, `generated_at`,
`generated_by`, `dictionary`, `rules`. Неизвестные поля запрещены
(`SETUP_UNKNOWN_FIELD`).

```json
{
  "schema": "masking-setup/v1",
  "generated_at": "2026-09-26T12:00:00Z",
  "generated_by": {"kind": "agent", "name": "<агент>", "note": "первичная настройка"},
  "database_hint": {"id": "<uuid базы>", "label": "<имя>", "source_version": 1},
  "dictionary": {
    "mode": "part",
    "sources": [
      {
        "source_path": "Справочник.ФизическиеЛица.ФИО",
        "category": "FIO",
        "reason": "ПДн: ФИО сотрудников",
        "estimated_values": 4200,
        "filter": {"op": "eq", "field": "ПометкаУдаления", "value": false}
      },
      {
        "source_path": "Справочник.Контрагенты.КонтактнаяИнформация.Представление",
        "category": "PII",
        "reason": "ПДн: телефоны и адреса контрагентов (ТЧ БСП 3.x)"
      }
    ]
  },
  "rules": [
    {
      "selector": "name", "value": "*apiKey*", "action": "mask",
      "category": "SECRET", "enabled": true, "priority": 0,
      "reason": "Секрет: имя содержит apiKey"
    },
    {
      "selector": "name", "value": "*паспорт*", "action": "mask",
      "category": "PII", "reason": "ПДн: имя содержит «паспорт»"
    },
    {
      "selector": "name", "value": "*фио*", "action": "mask",
      "category": "FIO", "reason": "ПДн: имя содержит «фио»"
    },
    {
      "selector": "source_path", "value": "Справочник.Контрагенты.НаименованиеПолное",
      "action": "mask", "category": "FIO",
      "reason": "ПДн: полное наименование контрагента"
    },
    {
      "selector": "dictionary", "value": "FIO", "action": "mask",
      "category": "FIO", "reason": "Действие для словарной категории FIO"
    },
    {
      "selector": "dictionary", "value": "PII", "action": "mask",
      "category": "PII", "reason": "Действие для словарной категории PII"
    }
  ]
}
```

У `rules[]` два опциональных поля, которые в экспорте присутствуют
всегда: `enabled` (bool, по умолчанию `true` — выключенное правило
хранится, но не действует) и `priority` (int, по умолчанию `0` —
тай-брейк между равными действиями). У `sources[]` этих полей нет.
При переносе из экспорта сохранять как есть.

## Приложение: профили предметных областей (подсказки, не правила)

Типовые имена БСП: `ФизическиеЛица`, `Контрагенты`, `Пользователи`;
контактная информация в БСП 3.x — **табличная часть**
`КонтактнаяИнформация` каждого справочника (поля `Представление`,
`ЗначенияПолей`), а не регистр сведений — проверять по структуре
конкретной конфигурации. Профиль
подсказывает, где искать и что обычно чувствительно; решение всегда
за каталогом классов + анкетой.

| Область | Типичные объекты/маркеры | Обычно чувствительно |
|---|---|---|
| Торговля/ERP | `Контрагенты`, `Партнеры`, `ЗаказКлиента`, `СоглашениеСКлиентом`; `цена`, `скидка`, `партнер` | клиенты-физлица, индивидуальные цены/скидки |
| HR/зарплата | `Сотрудники`, `ФизическиеЛица`, `Начисление*`, `Ведомость*`; `оклад`, `начислено`, `удержано` | всё о сотрудниках; начисления как числа — по анкете п.3 |
| Медицина | `Пациенты`, `Прием`, `МедицинскаяКарта`, `Диагноз*`; `диагноз`, `жалобы`, `анализ` | пациенты целиком, особые категории — включая справочники диагнозов в записи пациента |
| Банк/финансы/учёт | `БанковскиеСчета`, `Карты`, `Выписка*`, `Остатки*`; `счет`, `карта`, `iban`, `остаток` | счета и остатки конкретных клиентов |
| Бюджет/госсектор | `Граждане`, `Льгота*`, `Заявление*`; `льгота`, `субсидия`, `получатель` | граждане, льготы, выплаты |
| CRM | `Контакты`, `Лиды`, `Взаимодействия`, `Переписка*`; `контакт`, `email`, `телефон` | контакты и переписка (словарь+regex для текстов) |
| Биржа/крипто | `Аккаунты`, `Ордера`, `Сделки`, `Кошельки`; `ordid`, `clordid`, `tradeid`, `wallet`, `subaccount`, `apikey`, `secretkey`, `passphrase` | аккаунты, API-ключи/passphrase (секреты → граница), кошельки; ID ордеров/сделок — по анкете п.5 |

## Серые зоны — вопросы человеку

Навык не решает сам; по каждой зоне в отчёте — выбранное умолчание,
почему, альтернатива:

- данные собственной организации (наша ИНН/реквизиты в документах —
  обычно открыто, но бывает требование);
- справочники с чувствительным составом (номенклатура аптеки/оружия —
  состав списка может сам быть тайной);
- технические ID, похожие на внешние (`ДоговорНомер`, `КодЗаказа` —
  внешний идентификатор или внутренний реквизит?);
- представления/серии документов, в которые зашит номер и дата
  (композитный идентификатор события);
- исторические/архивные записи (тот же класс, но старые данные —
  фильтр словаря или исключение?).

## Проверка перед отдачей (самоконтроль)

Самопроверка выполняется **без импорта** — импорт и diff делает
человек. Агентская проверка: синтаксис JSON (парсер), чек-лист
ниже, подтверждение каждого `source_path` через `get_metadata`.
Отдельного JSON-схема-файла в репозитории сервиса нет — схема
зашита в код (`SETUP_SCHEMA`, `src/domain/setup/parse.rs`).

- `schema` = `masking-setup/v1`; верхнеуровневые поля только из схемы;
  вложенные объекты — без лишних ключей.
- `generated_by.kind` = `agent`; у каждого `sources[]`/`rules[]`/
  `tools[]` есть непустой `reason` (≤500); `note` содержит итог
  анкеты/факт умолчаний.
- `dictionary.mode` = `part` и ни одного `source_path="*"`, **или**
  `all` и ровно один источник `"*"`.
- Нет повторов `source_path` (без учёта регистра) в `sources`; нет пар
  `(selector, value)`-дублей в `rules` (регистронезависимо для
  source_path/name/type/dictionary; regex — байт-в-байт); нет дублей
  `tools[].tool`.
- Шаблоны `*` только в формах `*` или `*x*`; `*.x`/`x.*` запрещены
  (`SETUP_PATTERN_UNSUPPORTED`).
- `tests` только у regex-правил; у mask/secret-regex есть
  `tests.match` ≥1 и все `no_match` не совпадают с regex.
- `enabled`/`priority` — только в `rules[]` (bool/int); в
  `sources[]` их нет.
- `filter` — только ops `and/or/not/eq/ne/in`, глубина ≤16,
  поля — имена реквизитов источника.
- Все `source_path`/`value` путей проверены по `get_metadata`
  (импорт иначе выдаст предупреждение `PATH_NOT_IN_MANIFEST`).
- Тело ≤1 МиБ; значений данных нет; секретов реальных нет.
- `action` везде `mask` (ни одного `secret` — иначе активация
  упадёт `SECRET_POLICY_UNSUPPORTED`, в diff будет предупреждение
  `SECRET_ACTIVATION_BLOCKED`).

## Жёсткие правила

- Не импортировать файл самим и не активировать: импорт, проверка
  diff и активация — зона человека в UI.
- Не запрашивать и не выводить реальные значения полей — настройка
  строится по именам и путям метаданных.
- Не писать `keep`-правила и не ослаблять существующую настройку
  без явного запроса человека.
- Не писать `secret`-правила; кандидатов в секреты — в отчёт как
  правку кода расширения (`ЭтоИмяСекрета`).
- Не выдумывать пути: каждый `source_path` подтверждён
  `get_metadata`; несуществующее помечать в отчёте.
- Не маскировать всё подряд: лишняя маска — дефект; сомнительное —
  в отчёт с «за/против», не молча скрывать.
